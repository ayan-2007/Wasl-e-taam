The Real-World Problem

1/3 of All Food Produced is Wasted. People Go Hungry Every Day.

According to the UN Food and Agriculture Organization, approximately 1.3 billion tonnes of food is lost or wasted every year globally — enough to feed the world's hungry population three times over. In Pakistan alone, an estimated 40% of perishable food is wasted at the retail and consumer level, while millions face food insecurity daily.

The core problem is not a shortage of food — it is a coordination failure. Restaurants prepare surplus food daily but have no efficient channel to connect with nearby shelters. NGOs spend hours manually calling donors. Volunteers have no centralized task pool. This is a software problem with a software solution.

What FoodBridge Does

FoodBridge is a console-based Java application (expandable to GUI/web) that acts as a coordination hub between four actor types: Donors, Recipients, Volunteers, and Admins. When a donor posts surplus food, the system automatically notifies eligible recipients, applies a smart matching strategy, tracks the donation through its full lifecycle via a state machine, records every action in an audit trail, and updates a live impact dashboard. Every component is driven by a canonical design pattern — no pattern is decorative.

Core Purpose

Real-Time Donor–Recipient Matching

Donors post food. Recipients claim it instantly. Volunteers collect and deliver — all tracked end-to-end.

Project Overview

System Actors & Key Features

FoodBridge has four primary actors. Each actor interacts with a distinct set of use cases and represents a real-world stakeholder in the food redistribution ecosystem.

Actor 1

🍽️ Donor

Restaurants, hotels, grocery stores, catering companies, or individuals who post surplus food listings with quantity, type, and expiry.

Actor 2

🏠 Recipient

NGOs, food banks, orphanages, shelters — organizations that claim donations and distribute them to beneficiaries.

Actor 3

🚗 Volunteer

Logistics volunteer who picks up food from the donor location and delivers it to the recipient's address.

Actor 4

🛡️ Admin

Platform administrator who manages users, resolves disputes, switches matching strategy at runtime, and generates audit reports.

Key Differentiating Features

Feature 1

Expiry-Aware Priority Escalation

Donations within 2 hours of expiry are auto-flagged URGENT and jump the matching queue — preventing food from being thrown away.

Feature 2

Full Undo-able Audit Trail

Every claim, cancel, and delivery is a Command object — supporting legal-grade audit reporting and one-click undo of any action.

Feature 3

Live Impact Dashboard

kg saved, meals served, CO₂ offset, top donors, top recipients — auto-updated in real time via Observer pattern.

Feature 4

Pluggable Matching Algorithms

Admin switches between Nearest-First, Expiry-First, or Capacity-Based matching at runtime — zero code changes required.

Design Patterns

Six Patterns — Six Real Problems Solved

Every pattern below solves a concrete problem. Removing any one of them would cause a real architectural failure — they are not decorative.

Pattern 1 · Behavioral — Observer

Observer Pattern — Real-Time Notifications & Decoupled Event Propagation

Problem solved: When a new donation is posted, multiple subsystems must react: recipients must be notified, the dashboard must update, the audit log must record the event, and the expiry watcher must start monitoring. Hardcoding these calls inside the coordinator creates tight coupling and makes adding any new listener (e.g., SMS gateway) require modifying core business logic.
How it works: DonationCoordinator holds a list of SystemObserver implementors. On every significant event (donation posted, claimed, delivered), it calls notifyAll(event). Each observer reacts independently: RecipientNotifier alerts eligible recipients, ImpactDashboard increments counters, AuditLogger persists the record, ExpiryWatcher schedules an expiry check.
Why it matters: Adding an SMS notification service requires zero changes to business logic — just implement SystemObserver and register. Open/Closed Principle fully upheld.

SystemObserver.java RecipientNotifier ImpactDashboard AuditLogger ExpiryWatcher
Pattern 2 · Behavioral — Strategy

Strategy Pattern — Swappable Matching Algorithms at Runtime

Problem solved: The ideal way to match a food donation to a recipient changes based on context: during normal hours, use nearest-first to minimize spoilage. During crisis, use capacity-based to maximize meals served. On urgent donations, use expiry-first regardless of distance. Baking any single algorithm into the coordinator makes switching impossible without risky code changes.
How it works: MatchingEngine holds a reference to a MatchingStrategy interface. Admin calls engine.setStrategy(new ExpiryFirstStrategy()) at runtime. The engine calls strategy.findBestMatch(donation, recipients) — it never knows which concrete algorithm it is using.
Why it matters: Adding a new algorithm (e.g., ML-based scoring) requires implementing one interface and one line of wiring. All existing algorithms are untouched.

MatchingStrategy.java NearestFirstStrategy ExpiryFirstStrategy CapacityBasedStrategy
Pattern 3 · Creational — Factory Method

Factory Pattern — Dynamic Domain Object Creation

Problem solved: Different donation types (perishable, dry food, prepared meals) have different attributes, validation rules, and expiry behaviors. Different user roles have different permissions. Allowing callers to use new PerishableDonation() directly spreads construction logic everywhere and makes adding a new type require finding and updating all new call sites.
How it works: DonationFactory.create("PERISHABLE", params) returns the correct subclass. UserFactory.create("DONOR", params) returns a Donor. All construction logic lives in one place.
Why it matters: Adding a new donation type — say, FrozenFoodDonation — requires adding one class and one factory case. No other code changes anywhere in the system.

DonationFactory.java UserFactory.java PerishableDonation DryFoodDonation PreparedMealDonation
Pattern 4 · Behavioral — State

State Pattern — Donation Lifecycle Management

Problem solved: A donation exists in 7 distinct states with different legal transitions (you cannot claim an IN_TRANSIT donation; you cannot deliver an EXPIRED one). Without the State pattern, the coordinator becomes a massive if-else chain with state-checking logic tangled through every method — violating Single Responsibility massively.
How it works: Each state is a class implementing DonationState. The Donation object holds a reference to its current state. When an action is called (e.g., donation.claim(recipient)), the call delegates to the current state object, which either performs the legal transition or throws an illegal-state exception.
Why it matters: Each state class encapsulates exactly what is legal in that state. No if-else chains. Adding a new state requires one new class only.

DonationState.java AvailableState ClaimedState InTransitState DeliveredState ExpiredState
Pattern 5 · Behavioral — Command

Command Pattern — Undoable Actions & Full Audit Trail

Problem solved: Every action (claiming, cancelling, delivering) must be: (a) undoable in case of errors, (b) logged for legal accountability, (c) replayable for dispute resolution. Calling methods directly makes none of these possible without massive infrastructure bolted onto the outside of the system.
How it works: Every user action is wrapped in a DonationCommand with execute() and undo(). The CommandInvoker maintains a stack of executed commands. Undo pops and reverses the state transition. AuditTrail records every executed command with timestamp, actor, and target.
Why it matters: Dispute resolution becomes trivial: replay the command history. ACM Code of Ethics §1.2 (accountability) is upheld by design — not as an afterthought.

DonationCommand.java ClaimDonationCommand CancelClaimCommand CommandInvoker AuditTrail
Pattern 6 · Behavioral — Chain of Responsibility

Chain of Responsibility — Multi-Step Donation Verification

Problem solved: Before a donation is made AVAILABLE, it must pass multiple sequential checks: Is it expired? Is the quantity non-zero? Is the donor location registered? Has admin approved it? Hardcoding all checks in one validator violates SRP and makes reordering or removing checks risky across the entire codebase.
How it works: Each check is a VerificationHandler subclass. Each handler holds a reference to the next handler. If a check passes, it calls next.handle(donation). If it fails, it returns a rejection with a specific reason. Chain assembled at startup: Expiry → Quantity → Location → Approval.
Why it matters: Adding a new check (e.g., food safety certification) requires one new handler class inserted into the chain — no existing handlers change.

VerificationHandler.java ExpiryCheckHandler QuantityCheckHandler LocationCheckHandler ApprovalHandler

SOLID Principles Alignment

S — Single Responsibility

One Class, One Reason to Change

Matching logic lives in MatchingEngine. Notification logic in RecipientNotifier. Persistence in Repository. Audit in AuditTrail. None overlap.

O — Open / Closed

Extend, Never Modify

New donation type via Factory. New matching algorithm via Strategy. New event listener via Observer. New verification step via Chain. Zero existing code touched in each case.

L — Liskov Substitution

Subtypes Honor Contracts

PerishableDonation, DryFoodDonation, PreparedMealDonation all behave as valid Donation objects everywhere Donation is expected.

D — Dependency Inversion

Depend on Abstractions

DonationCoordinator depends on MatchingStrategy interface, not concrete algorithms. Repository depends on interfaces, never on InMemoryRepo directly.

Development Roadmap

Phased Build Milestones

Follow this order strictly. Each milestone produces independently testable output before the next begins. Each is assigned to reduce parallel conflict between team members.

M1

Domain Model & Factory (Week 1–2) — Member A

Define abstract Donation and User. Implement all three Donation subclasses and all four User subclasses. Implement DonationFactory and UserFactory. Write JUnit tests asserting correct subtype creation from string input. Get domain foundations rock-solid before anything else.

M2

State Machine & Chain of Responsibility (Week 2–3) — Member A

Implement all 6 DonationState classes with legal transition enforcement (throw exception on illegal transitions). Implement 4 VerificationHandler subclasses and assemble default chain. JUnit: assert expired donation rejected at ExpiryCheckHandler; assert valid donation passes all handlers and reaches AVAILABLE state.

M3

Command Pattern & Audit Trail (Week 3–4) — Member B

Ethics & Society — PLO 8 & 9

Ethical Dimensions of Algorithmic Food Redistribution

FoodBridge operates at the intersection of social good and software responsibility. Building a system that redistrib­utes food to vulnerable populations creates ethical obligations that connect directly to computing professionalism standards.

1. Liability & Food Safety — Who is Responsible?

If a recipient NGO distributes donated food that causes illness, who bears legal responsibility — the donor, the volunteer, or the platform? FoodBridge's Chain of Responsibility (which rejects expired donations) and full AuditTrail (Command pattern) create a timestamped, immutable record of every actor's action, directly addressing ACM Code of Ethics §1.2 (avoid harm) by providing accountability. The software itself acts as a safety gate — not just a passive connector.

2. Algorithmic Equity — Efficiency vs. Fairness

The NearestFirst matching strategy efficiently minimizes food spoilage transit time, but it systematically favors recipients near wealthy donor-dense city centers, while rural or peripheral shelters — often serving the most vulnerable — receive fewer donations. FoodBridge's Strategy pattern makes this trade-off explicit and reconfigurable: an admin can consciously choose a NeedFirst algorithm. The act of choosing a matching algorithm is an ethical decision, not just a technical one — this is a powerful point to make during your defense.

3. Location Privacy — Where People Seek Help

Both donors and recipients must register physical locations for the matching algorithm to function. Recipient shelter locations may house at-risk individuals (domestic violence survivors, undocumented persons). Should exact addresses be shared with volunteers? FoodBridge should anonymize location data to proximity zones rather than exact coordinates — a deliberate architectural privacy-by-design decision aligned with ACM Code §1.6 (respect privacy).

4. Algorithmic Bias in Recipient Scoring

If the system tracks recipient reliability scores (e.g., failure-to-collect rate) and factors them into matching, a small NGO that missed one pickup due to a vehicle breakdown may be penalized indefinitely. Bias in social welfare allocation has real human costs. FoodBridge's ImpactDashboard should report distribution equity metrics — not just total volume — giving administrators data to identify and correct systemic bias in outcomes before it entrenches.

Future Work — PLO 10

Where FoodBridge Can Grow

The architecture is deliberately designed to accommodate these extensions without modifying existing code — each represents a natural growth path enabled by the patterns already in place.

AI / ML

Predictive Demand Forecasting

Train a model on historical patterns to predict which areas will have surplus or deficit food — implement as a new MatchingStrategy without touching existing algorithms.

Interface

JavaFX / Web Dashboard

Replace ConsoleUI with JavaFX or Spring Boot REST. Observer pattern makes this a drop-in — UI is just another Observer on the existing event bus.

Notifications

WhatsApp / SMS Alerts

Implement SystemObserver backed by Twilio API. Zero changes to business logic — one new Observer class registered at startup.

Trust

Blockchain Audit Trail

Replace file-based AuditTrail with an immutable blockchain ledger. Command pattern already produces the perfect transaction record — persisting it differently is a storage swap.

Engagement

Volunteer Gamification

Track volunteer impact points per delivery (Observer on DELIVERED events). Leaderboard and badge system to incentivize consistent volunteering — zero core changes.

Scale

Multi-City Federation

Each city runs its own FoodBridge instance. Cross-city routing when local demand is saturated. Architecture already supports clean separation at the coordinator level.
